# 개발 환경의 평가와 방향

## 목적과 평가 기준

이 프로젝트의 목표는 환경이 달라져도 가능한 한 동일한 개발 환경과 작업 경험을 유지하는 것입니다.
개별 설정 파일의 호환성뿐 아니라 터미널 실행, 프로젝트 전환, 창 이동, 편집, 검색, Git 작업, 클립보드와 한글 입력까지 이어지는 흐름을 기준으로 평가합니다.

평가는 2026-10-02 기준 `main`의 설정과 설치 스크립트를 정적으로 검토한 결과입니다.
검토 기준 커밋은 `941ff6f`입니다. 회사 Windows 노트북에서의 실행과 전체 플러그인 기능은 아직 검증하지 않았습니다.

## 사용 환경과 확정된 요구사항

| 환경 | 사용 이력 및 요구사항 |
| --- | --- |
| macOS | 기존 사용 환경이며 앞으로도 유지합니다. |
| Windows + WSL | 과거 사용 환경입니다. 기존 설정의 의도를 이해하는 기준으로 유지하되 회사 환경의 전제로 삼지 않습니다. |
| Windows 네이티브 + PowerShell | 회사 노트북의 새 요구사항입니다. 보안 정책상 WSL은 사용할 수 없습니다. |
| 네이티브 Linux | 사용 이력이 없고 검증되지 않았습니다. 공통 설정에서 불필요하게 배제하지 않되 초기 완료 조건으로 삼지는 않습니다. |

macOS와 회사 Windows 모두 LazyVim을 사용합니다.
WezTerm을 공통 터미널로 삼아 화면과 작업 방식을 최대한 공유하는 방향으로 검토합니다.
셸 문법과 모든 명령을 동일하게 만드는 것은 필수 요구사항이 아닙니다.
회사 환경에서 설치·사용할 수 있는 도구의 범위는 별도로 확인해야 합니다.

## 현재 구성 평가

공통화할 구성요소는 이미 있지만, 파일마다 환경 가정이 달라 하나의 작업 환경으로 연결하는 기준이 부족합니다.
macOS와 WSL에서는 Unix 셸과 tmux를 공유해 차이가 작았으나 Windows 네이티브에서는 해당 기능을 어디에서 제공할지 결정해야 합니다.

| 영역 | 현재 상태 | 보완 방향 |
| --- | --- | --- |
| WezTerm | 색상·글꼴·키맵을 정의하지만 Windows 실행은 고정된 WSL 배포판과 사용자 경로를 전제로 합니다. | 공통 화면과 키맵을 유지하고 OS별 기본 셸과 경로를 분리합니다. |
| Neovim / LazyVim | 편집·검색·Git·AI와 언어 도구 설정을 공유할 기반이 있습니다. OS 판별과 일부 빌드·연동은 Unix 환경을 가정합니다. | 공통 플러그인과 키맵을 유지하고 외부 도구·클립보드·빌드를 환경별 처리합니다. |
| tmux / 프로젝트 세션 | 창 이동과 `scripts/t`의 프로젝트 전환에 사용합니다. | Windows에서도 제공할 작업을 먼저 정의하고 구현 수단을 선택합니다. |
| fish / zsh | 개인 경로, 외부 도구, SSH 호스트를 포함하며 PowerShell 설정은 없습니다. | 셸별 구현을 허용하되 자주 쓰는 작업의 이름과 흐름을 가능한 범위에서 맞춥니다. |
| 한글 입력 | macOS의 Hammerspoon과 Windows의 AutoHotkey가 입력 전환을 처리합니다. | Esc 이후 입력 상태 등 공통 기대 동작을 정하고 OS별로 검증합니다. |
| 설치 | Unix 설치 스크립트가 기존 설정을 삭제하고 링크합니다. 일부 경로와 셸 표현에도 제약이 있습니다. | 백업·복구와 선택 적용을 지원하고 OS별 설치 절차를 마련합니다. |

구체적인 확인 사항:

- Neovim과 WezTerm이 `HOME` 문자열로 OS를 추측합니다.
- WezTerm의 WSL 배포판 `WSL:Ubuntu-22.04`와 `/home/locate`가 고정되어 있습니다.
- CopilotChat의 `make tiktoken` 빌드를 조건 없이 실행하도록 설정되어 있습니다.
- Neovim 창 이동은 tmux 이동 명령에, tmux 복사는 macOS의 `pbcopy`에 연결되어 있습니다.
- fish에는 macOS 개인 경로와 미리 설치된 도구를 전제로 한 호출이 있습니다.
- Alacritty의 여러 키맵은 tmux 제어 입력을 전송합니다. WezTerm에서 같은 작업을 제공하는지는 별도 검토가 필요합니다.
- 기존 설치 스크립트는 WezTerm과 zsh 설정을 자동으로 연결하지 않습니다.

Lua로 작성된 설정이나 플러그인도 외부 실행 파일을 호출할 수 있습니다.
Lua 설정을 공유하는 것과 외부 도구를 포함한 기능이 모든 환경에서 동작하는 것은 별도로 검증해야 합니다.

## 공통 설정과 환경별 구현의 경계

공통 설정에는 사용자가 반복해서 익히는 동작을 둡니다.
OS별 설정에는 해당 동작을 구현하는 데 필요한 차이를 둡니다.

| 공통으로 유지할 대상 | 환경별로 처리할 대상 |
| --- | --- |
| 터미널 색상·글꼴·화면 구성 | 기본 셸과 실행 경로 |
| 편집 옵션·키맵·플러그인 구성 | OS 기능 탐지와 선택적 의존성 |
| 검색·자동완성·진단·Git 작업 흐름 | 검색 도구·언어 서버·포매터 실행 파일과 설치 |
| 복사·붙여넣기의 기대 동작 | 클립보드 provider |
| 창 분할·이동·프로젝트 전환 동작 | WezTerm, tmux, Neovim의 역할 분담 |
| 한글 입력 상태와 Esc의 기대 동작 | Hammerspoon·AutoHotkey 등 입력 처리 방식 |

개인 경로, SSH 호스트, 계정 정보와 회사 전용 설정은 공유 설정과 구분하는 방향으로 검토합니다.
누락된 선택적 도구는 해당 기능을 제한하되 전체 환경의 시작을 막지 않도록 설계합니다.
필수 도구와 선택적 도구의 목록은 기능 범위를 정한 뒤 확정합니다.

## 우선 결정할 설계 사항

### 창과 세션 관리

WezTerm은 pane, tab, workspace 기능을 제공하므로 공통 창 관리의 후보입니다.
tmux의 지속 세션과 원격 작업까지 동일하게 대체한다고 가정하지 않습니다.
macOS에서 tmux를 계속 사용할지, 로컬 작업의 창 관리를 WezTerm으로 맞출지는 아직 결정하지 않았습니다.

프로젝트 전환도 현재의 Bash 기반 `scripts/t`를 그대로 Windows에 이식하기 전에 기대 동작을 정해야 합니다.
프로젝트 디렉터리 선택, 기존 작업 재사용, 새 작업 생성과 세션 복원을 구분해서 검토합니다.

### 키 입력의 담당 계층

터미널, 셸 또는 tmux, Neovim 사이에서 각 키를 어느 계층이 처리하는지 정해야 합니다.
예를 들어 WezTerm의 `Ctrl+V` 붙여넣기는 Neovim의 Visual Block 키와 충돌할 수 있습니다.
복사·붙여넣기, 분할·이동·닫기, Esc와 한글 입력 전환은 실제 입력 경로를 따라 검증합니다.
macOS의 Command와 Windows의 Control/Alt 차이는 같은 작업을 수행하도록 맞추되 물리적으로 모든 키를 같게 만드는 것을 전제로 하지 않습니다.

### 회사 환경의 사용 가능 도구

PowerShell 버전과 WezTerm, Git, Node.js, 검색 도구, 컴파일러 등의 설치 가능 여부를 확인해야 합니다.
CopilotChat 등 외부 AI 서비스의 사용 가능 여부도 기능 범위에 반영합니다.
이 문서는 특정 도구의 회사 사용 승인을 가정하지 않습니다.

## 제안하는 진행 순서

1. **현재 작업 흐름 기록:** 실제 사용하는 터미널·셸·키맵·프로젝트 전환 방식을 확인합니다.
2. **공통 기대 동작 정의:** 시작, 분할·이동, 검색, Git, 복사·붙여넣기, 입력 전환과 복원을 정합니다.
3. **환경별 기능표 확정:** macOS와 Windows에서 필요한 도구, 대체 구현, 제외 기능을 정합니다.
4. **설치와 작업 환경 분리:** 기존 설정의 백업·복구 방법과 실제 사용 체크아웃에서 분리된 수정 환경을 마련합니다.
5. **작은 단위로 구현·검증:** WezTerm 시작과 키맵, LazyVim 기본 기능, 외부 도구 및 입력 연동을 순차적으로 검증합니다.
6. **문서와 협업 지침 반영:** 검증된 설치 절차와 제한을 README에 반영하고 분석 → 계획 → 수정 → 검증 → PR 순서를 지침으로 정리합니다.

세부 구현과 우선순위는 미결정 사항을 확인한 뒤 확정합니다.
기존 Neovim 수정안과 AI 가드레일 PR도 이 기준에 맞는지 재검토합니다.
이 문서는 평가와 방향을 기록하며 기존 수정안의 적용이나 PR 병합을 승인하는 문서가 아닙니다.

## 검증 기준

검증은 플러그인 설치 성공뿐 아니라 공통 작업의 완료 여부로 판단합니다.

| 시나리오 | 확인할 결과 |
| --- | --- |
| 터미널과 편집기 시작 | 의도한 셸로 시작하고 LazyVim이 오류 없이 열립니다. |
| 화면과 키 입력 | 글꼴·아이콘이 표시되고 터미널과 Neovim 키맵이 충돌하지 않습니다. |
| 창과 프로젝트 이동 | 정한 키와 흐름으로 분할·이동·프로젝트 전환을 수행합니다. |
| 편집과 언어 도구 | 정한 언어에서 자동완성·진단·포맷 기능이 동작합니다. |
| 검색과 Git | 파일·텍스트 검색과 Git 화면이 정상 동작합니다. |
| 클립보드와 입력 전환 | 한글·여러 줄 복사 및 붙여넣기, Esc 이후 입력 상태가 기대와 일치합니다. |
| 설치와 복구 | 개인 설정을 보존하며 적용하고 이전 상태로 복구할 수 있습니다. |

macOS와 Windows 네이티브에서 각각 확인하고, 확인하지 못한 기능은 미검증으로 기록합니다.
WSL의 기존 동작도 유지 범위가 확정되면 회귀 검증 대상으로 포함합니다.
