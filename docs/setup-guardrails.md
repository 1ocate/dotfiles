# 공통 설정과 환경 연결 원칙

2026-10-03 기준 방향은 **공통 설정을 원본으로 두고 스크립트는 환경 차이를 연결하는 것**이다. 셸 문법까지 같게 만들기보다는 편집, 검색, 복사, 터미널 이동 같은 작업 흐름을 맞춘다.

| 계층 | 역할 | 현재 원본 또는 연결 |
| --- | --- | --- |
| 공통 설정 | 편집기·터미널 동작과 플러그인 | `nvim/`, `.wezterm.lua` |
| 환경 연결 | 플랫폼별 경로·셸·클립보드·IME | 설정 내 작은 OS 분기, `use-wezterm.ps1`, `use-neovim.ps1`, `autoHotKey.ahk` |
| 설치 | 의존성 점검·설치, 원본 연결 | 임시 `setup-windows.ps1` |
| 장비별 정보 | 인증·회사 정책·개인 경로 | 저장소 밖에서 관리, 자동 배포 제외 |

Windows는 PowerShell 7을 사용하고 macOS는 기존 셸을 유지한다. Windows용 Neovim/WezTerm 설정을 별도로 복제하지 않는다. 공통으로 표현할 수 없는 차이만 플랫폼 또는 기능 유무로 분기한다. 설치 시 생성하는 loader의 체크아웃 절대 경로는 연결 정보이며 공통 설정에 고정하는 장비 경로와 구별한다.

## 환경 정의와 판별

설치와 설정 로드에 사용하는 환경 이름은 다음 네 가지로 고정한다. `common`은 환경 이름이 아니라 공유 설정의 적용 범위다.

| 환경 ID | 정의 | 기본 변경 범위 |
| --- | --- | --- |
| `macos` | Darwin/macOS에서 실행 | macOS 사용자 설정 |
| `windows-wsl` | WSL 내부의 Linux에서 실행 | 해당 WSL 배포판의 사용자 설정 |
| `windows-powershell` | Windows 네이티브에서 실행 | Windows 사용자 설정 |
| `linux` | WSL이 아닌 네이티브 Linux에서 실행 | Linux 사용자 설정 |

판별은 실행 중인 프로세스의 플랫폼 정보부터 확인한다. Darwin이면 `macos`, Windows이면 현재 실행 환경은 `windows-powershell`이지만 설치할 사용 환경은 별도 승인으로 정한다. Linux이면 WSL 여부를 먼저 확인해 `windows-wsl`과 `linux`를 구분한다. WSL 신호는 `WSL_INTEROP`·`WSL_DISTRO_NAME`과 커널 정보의 Microsoft/WSL 표식을 사용하며, 하나의 환경 변수 부재만으로 WSL을 배제하지 않는다. 플랫폼·WSL 신호가 충돌하거나 판별 정보를 얻을 수 없으면 근거를 출력하고 적용 전에 중단한다. HOME 문자열, 사용자 이름, 체크아웃 위치로 판별하지 않는다.

`windows-powershell`은 셸 버전이 아니라 Windows 네이티브 환경을 뜻한다. PowerShell 5.1로 설치를 시작해도 같은 환경이며, 이후 사용할 PowerShell 7은 의존성으로 준비한다. Linux에서 PowerShell을 실행해도 플랫폼에 따라 Linux 또는 WSL로 분류한다.

환경 판별은 현재 실행 위치에 대한 것이며, 사용할 터미널 도메인이나 원격 호스트 선택과 구분한다. Windows WezTerm 설정은 Windows 환경에서 로드되고 그 안의 WSL Neovim은 WSL 환경에서 로드된다. WSL 설치가 Windows 홈·레지스트리·시작프로그램을 자동으로 수정해서는 안 된다. 호스트 간 연결이 필요한 기능은 변경 대상을 따로 표시하고 명시적으로 요청된 범위에서만 적용한다.

네 환경은 설계상의 구분이다. 회사 장비에서는 WSL을 사용하거나 보안 정책을 우회하지 않는다. 현재 임시 설치 진입점은 Windows 네이티브만 처리하며, 나머지 환경의 통합 설치와 검증 완료를 의미하지 않는다.

## Windows 사용 환경 선택과 승인

Windows 자동 감지는 현재 실행 위치를 알려주는 점검이며 PowerShell 설치·연결에 대한 승인이 아니다. 첫 설정에서는 사용할 환경과 적용 계획을 제시하고 사용자가 `windows-powershell` 또는 `windows-wsl`을 명시적으로 선택한 뒤 설치·연결을 진행한다. WSL 안에서 설치를 시작해도 실행 위치만으로 최초 사용 승인을 추정하지 않는다. 회사 정책으로 WSL이 금지된 호스트는 PowerShell만 제시하되 그 사용 선택도 확인한다. 사용자가 이미 해당 호스트의 PowerShell 설치·사용을 명시적으로 요청했다면 그 요청을 승인으로 인정하며 반복해서 묻지 않는다.

승인된 선택은 향후 설치 구현에서 호스트별 로컬 상태로 보존한다. 저장 위치는 Git에서 제외된 `.local/environment.json`을 기준으로 하며, 환경 ID, 호스트 식별, 승인 시각과 근거를 기록한다. 환경 ID나 파일 존재만으로 유효한 승인으로 판단하지 않고 현재 호스트·실행 환경과 일치하는지 확인한다. 다른 호스트로 승인 파일을 복사하거나 Git으로 배포하지 않는다. 호스트 식별 정보는 로컬에만 두며 비밀 정보는 저장하지 않는다.

같은 호스트에서 유효한 선택을 유지하는 재실행은 재승인을 요구하지 않는다. 환경을 바꾸려는 경우, 호스트가 달라진 경우 또는 저장된 선택과 실제 실행 위치가 다른 경우에는 적용 전에 확인한다. WSL을 선택한 상태로 Windows에서 실행했다면 PowerShell로 자동 전환하지 말고 선택한 WSL에서 실행하도록 안내한다. 선택 변경 시 이전 환경 설정을 자동 삭제하지 않는다.

비대화형 설치도 동일하게 적용한다. 유효한 기존 승인이나 해당 호스트·환경을 지정한 명시적 사용자 지시가 없으면 설치·연결을 중단하고 선택 방법을 안내한다. 경과 시간, 기본 선택값, PowerShell 실행 여부, Codex의 승인 생략 옵션은 사용 환경 선택에 대한 동의로 간주하지 않는다. 계획·읽기 전용 점검은 승인 없이 가능하다. 편집기·터미널의 매 시작마다 승인 질문을 띄우지는 않는다.

현재 Windows 장비는 이 대화에서 PowerShell 사용과 설치를 이미 승인했으므로 선택을 유지하고 재승인하지 않는다. 이는 이 장비에 대한 승인 이력이며 다른 호스트의 기본 승인이 아니다. Windows 설치와 연결 스크립트는 `-ApprovePowerShell`로 명시한 선택을 `.local/environment.json`에 저장하고 다음 실행에서 호스트 일치를 검사한다. 대화의 기존 승인은 자동으로 파일에 기록되지 않으므로, 이미 승인된 환경을 설치할 때 해당 옵션을 전달해 기록한다. 토큰 등이 들어 있는 `.local/` 폴더를 새 호스트로 복제하지 않는다.

## 설정 범위와 격리

각 변경은 시작 전에 `common` 또는 환경 ID의 목록으로 적용 범위를 선언한다. 공유 파일 안에 있는 작은 환경 분기도 해당 환경 전용 범위로 취급한다. 한 환경에서 발견한 문제를 해결할 때 공통 동작까지 바꾸려면 다른 환경에서도 그 변경이 필요한 이유를 기록한다.

- `common`: 지원 환경 전체에서 공유하는 동작. 외부 도구가 필요하면 필수·선택 여부와 부재 시 처리를 정의한다.
- 환경 전용: 경로, 셸, 클립보드, IME, 설치 도구 등 해당 환경의 차이. 현재 환경이 일치할 때만 로드·실행한다.
- 여러 환경 전용: 예를 들어 Linux와 WSL의 공통 구현을 공유할 수 있지만 적용 환경 목록을 명시한다. 파일 확장자나 사용 언어로 실행 환경을 추측하지 않는다.

로드 순서는 공통 설정 → 현재 환경의 차이 적용이다. 다른 환경 모듈은 import/require 시점부터 실행하지 않는다. 모든 환경 모듈을 먼저 로드하고 뒤에서 선택하는 방식은 피한다. 환경 전용 진입점도 자체 환경 검사를 수행해 직접 실행 시 잘못된 호스트 변경을 막는다.

Windows 네이티브 프로세스에서 OS 감지와 PowerShell 선택은 별개다. 설치·연결뿐 아니라 Neovim과 WezTerm도 현재 호스트의 `.local/environment.json`을 확인하고 `windows-powershell`로 승인된 경우에만 해당 분기를 적용한다. 기록 부재·손상·호스트 불일치에서는 안내 후 PowerShell 분기를 적용하지 않으며, 저장된 WSL 선택을 PowerShell로 바꾸지 않는다. Unix에서는 이 Windows 선택 파일을 읽지 않는다.

공통 원본을 유지하면서 전용 모듈을 분리할 수 있다. 예를 들어 Neovim 전체를 OS별로 복제하는 대신 공통 옵션과 환경별 차이 모듈을 둔다. 모듈 경로는 실제 구현 시 정하고, 문서의 환경 정의만으로 기존 파일을 일괄 이동하지 않는다. macOS 전용 키맵 수정은 Windows에서 로드되지 않아야 하며, 공통 키맵 수정은 네 환경의 영향 검토 대상이다.

## 일관적인 작업 순서

1. **환경 확인:** 플랫폼과 판별 근거, 실제 연결된 체크아웃을 확인한다.
2. **선택·범위·계획 기록:** Windows에서는 사용 환경을 명시적으로 선택하거나 기존 승인을 확인한다. 승인 전 설치·연결은 진행하지 않는다. 적용 환경, 변경할 원본, 연결 대상, 설치 도구를 명시한다. 비대상 환경의 경로는 적용 목록에서 제외한다.
3. **사전 점검:** 입력 파일·경로·기존 설정·정책·의존성 상태를 확인하고 누락된 설치 가능 도구와 진행을 막는 조건을 구분한다. 계획·점검 모드는 설정을 변경하지 않는다.
4. **의존성 준비:** 해당 환경의 패키지 도구만 사용한다. 준비 실패 시 설정 연결을 진행하지 않는다. 설치한 패키지까지 자동 롤백된다고 가정하지 않는다.
5. **원본 연결:** 기존 설정을 보존하고 공통 원본과 현재 환경 전용 설정만 연결한다. 같은 연결의 재실행은 중복 변경하지 않는다.
6. **범위별 검증:** 연결 대상·기본 실행·변경 기능과 비대상 환경에서의 미실행을 확인한다.
7. **Git 기록:** 관련 원본의 diff를 검토하고 저장소 제출 지침에 따라 기록한다. 인증·생성 파일·기존 무관한 변경을 포함하지 않는다.

변경 설명에는 `적용 범위`, `판별 근거`, `변경 원본/연결 대상`, `비대상 환경 영향`, `검증/미검증`을 남긴다. 비대상 환경 영향은 해당 모듈을 로드하지 않는 조건과 외부 명령·경로 쓰기가 실행되지 않는 근거로 설명한다. 공통 변경은 네 환경을 모두 검토하고 실제 실행하지 못한 환경은 미검증으로 표시한다. 전용 변경은 대상 기능 확인과 비대상 환경의 분기 격리를 확인한다.

## 호스트에서의 사용과 Git 기록

각 호스트에서 clone한 디렉터리가 실제 설정 원본이자 Git 작업 디렉터리다. 디렉터리를 원하는 안정적인 위치에 두고, 설치 스크립트가 프로그램의 설정 경로를 원본에 연결한다. 호스트 간 체크아웃의 절대 경로가 같을 필요는 없다. 위치를 바꾸면 연결을 다시 적용한다.

사용 흐름은 **clone → 경로 연결 → 원본 설정 수정 → reload/재시작 → diff 확인·commit → push → 다른 호스트에서 pull**이다. 변경사항이 작업 트리에 남는 것과 커밋 이력에 기록되는 것은 별개이며, 커밋은 diff를 검토한 뒤 수행한다. 파일 변경마다 자동 커밋하는 감시 기능을 의미하지 않는다. pull 전에는 해당 호스트의 로컬 변경을 보존하고 충돌을 처리한다.

심볼릭 링크나 junction을 통해 수정하는 파일도 저장소 원본을 변경한다. loader를 사용하는 프로그램은 loader 자체가 아닌 저장소의 설정 파일을 수정한다. 독립 복사본을 만든 뒤 변경을 다시 수집하는 방식이나 자동 양방향 동기화는 기본 구조로 삼지 않는다. 인증·캐시·플러그인 다운로드·장비 전용 정보는 공통 설정의 Git 기록에서 제외한다.

현재 Windows의 Neovim junction, WezTerm loader, 저장소 AutoHotkey 직접 실행은 이 구조를 따른다. PowerShell 사용자 프로필의 초기화 구문은 아직 호스트 파일에 기록되므로, 저장소 프로필을 읽는 연결 방식으로 바꾸는 후속 작업이 필요하다. macOS 설치 통합도 아직 완료하지 않았다.

## 실행 가드레일

1. 변경 전 OS, 입력 파일, 대상 경로, 필요한 실행 파일을 점검한다. 잘못된 환경에서 일부 설정만 먼저 바뀌지 않도록 한다.
2. 기존 설정은 백업하고 같은 연결이면 아무것도 변경하지 않는다. junction의 원본이나 대상이 서로 포함되는 연결은 거부한다.
3. 필수 기능의 실패는 명확하게 중단한다. 선택 기능은 skip 옵션으로 제외한다. 패키지 설치 제외와 기능 실행 제외는 별개다.
4. 설치는 잠금 파일을 보존한다. 회사 정책에 막힌 설치를 다른 경로로 우회하지 않는다.
5. `-Plan`은 계획 출력, `-Check`는 로컬 사전 점검만 수행한다. 둘 다 설치·설정 변경·프로그램 실행을 하지 않는다. 네트워크 접근과 설치 권한까지 보장하는 검사는 아니다.

Windows 설치의 읽기 전용 계획·점검은 다음 명령으로 수행한다. `-Check`는 설치하려는 도구도 이미 있어야 통과하므로 새 장비에서는 누락 목록 확인용이며, 설치 실행은 패키지 준비 후 다시 의존성을 점검한다. 최초 설치는 별도로 `-ApprovePowerShell`을 지정한다. 절차와 한계는 [Windows 설치 기록](windows-setup.md)에 정리한다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\setup-windows.ps1 -Plan
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\setup-windows.ps1 -Check
```
