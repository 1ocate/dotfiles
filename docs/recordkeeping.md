# 결정과 작업 기록 가드레일

지속적인 결정은 ADR(Architecture Decision Record)에, 작업의 이유·계획·결과는 작업 기록에 남긴다. README와 사용 문서는 현재 동작과 사용 방법을 설명하며 날짜별 작업 로그를 누적하지 않는다. 적용 범위는 `common`의 협업 절차이며 설치·런타임 동작 변경은 포함하지 않는다.

## 기록 위치와 기준

| 기록 | 원본 위치 | 내용 |
| --- | --- | --- |
| 결정 | `docs/adr/NNNN-주제.md` | 문제, 대안, 선택 이유, 영향과 재검토 조건 |
| 작업 계획과 로그 | `docs/work/NNNN-주제.md` | 요청 배경, 기준 커밋, 범위, 계획, 실제 변경·검증·남은 일 |
| 현재 사용 지침 | README, 환경·설치·협업 문서 | 현재 제공하는 동작, 제약, 실행 방법과 관련 기록 링크 |
| 리뷰와 코드 이력 | PR, Git | diff, 리뷰 논의, 커밋과 병합 상태 |
| 장비별 적용 상태 | `.local/environment.json`, `.local/setup-state.json` | 해당 호스트의 선택과 실제 적용 결과. 기존 [로컬 상태 기준](setup-guardrails.md#장비별-적용-진행-기록과-작업-재개)을 따른다. |

날짜는 기록의 속성으로 사용한다. 날짜별 파일·설치 후기·세션별 문서로 같은 작업을 나누지 않는다. ADR과 작업 기록은 각 디렉터리에서 독립적으로 증가하는 네 자리 번호를 사용하며 번호를 재사용하지 않는다. 새 번호는 기존 목록과 열린 PR을 확인해 정하고 충돌하면 병합 전에 조정한다. 번호는 순서 식별자이며 시간순 실행을 보증하지 않는다. 목록의 단일 진입점은 [ADR 목록](adr/README.md)과 [작업 목록](work/README.md)이다.

## ADR이 필요한 변경

여러 후속 작업의 기준이 되는 공통 구조, OS별 책임 경계, 설치·연결 방식, 의존성 정책, 키 입력의 담당 계층, 인증·권한·AI 협업 절차를 선택하거나 바꿀 때 ADR을 작성한다. 대안 중 하나를 선택한 이유와 비용을 남겨 다음 작업에서 같은 결정을 반복하지 않도록 한다.

오탈자·깨진 링크 수정, 이미 채택된 결정에 따른 작은 버그 수정에는 새 ADR이 필요하지 않다. 관련 ADR을 작업 기록에 연결하고 새 결정이 없음을 적는다. 기록 부담만 늘리는 파일별 ADR은 만들지 않는다.

새 결정은 구현 전에 `제안` 상태로 기록한다. 분석·가역적인 구현·검증은 요청 범위 안에서 계속 진행하며 ADR 작성 자체가 매 단계 사용자 확인을 추가하지 않는다. ADR 상태는 `제안`, `채택`, `기각`, `대체됨`으로 구분한다. 사용자 또는 PR 리뷰의 명시적인 채택 근거가 있으면 링크를 남긴다. 별도 결정 없이 ADR PR을 병합하면 해당 결정의 채택으로 간주하며, `제안` 문구가 남아 있으면 병합 이력을 근거로 다음 기록 갱신 시 `채택`으로 정리한다. 열린 PR과 push만으로 채택을 주장하지 않는다.

채택된 결정의 의미를 바꿀 때는 새 ADR을 만들고 양쪽을 연결한다. 새 ADR이 채택되면 이전 ADR을 `대체됨`으로 표시한다. 새 ADR이 제안·기각 상태라면 기존 결정은 유효하다. 기각·대체된 기록을 삭제하거나 과거 근거를 새 결정으로 덮어쓰지 않는다. 오탈자·링크·상태 정정은 가능하지만 정정 이유를 남긴다. 결정 채택은 코드 병합·설치·환경 선택·배포 승인이나 실기기 검증 완료를 뜻하지 않는다.

## 작업 기록의 생명주기

1. 분석 후 구현 전에 [작업 템플릿](work/template.md)으로 요청의 이유, 현재 문제와 미확인 사항, 기준 커밋·실행 환경, 대상·비대상 범위, 관련 ADR, 단계별 계획과 완료 조건을 기록한다. 문서 가드레일 변경도 작업 기록 대상이다. 단순 오탈자·링크 수정은 별도 파일 대신 PR 본문으로 이 항목들을 짧게 남길 수 있다.
2. 진행 중에는 같은 파일에 의미 있는 변화만 추가한다. 각 로그 항목은 시각과 시간대, 왜 진행했는지, 무엇을 수행했는지, 결과·근거와 다음 일을 포함한다. 도구 출력·채팅 전문·매 명령을 복제하지 않는다. 계획이 바뀌면 이전 계획과 변경 이유를 남긴다.
3. 검증은 환경, 검사 종류(실제 실행·정적·모의), 대상 커밋 또는 미커밋 diff, 명령·시나리오, 결과와 미검증 범위를 기록한다. 다른 OS의 모의 검사를 실기기 통과로 쓰지 않는다. 과거 보고를 옮길 때는 보고 원본과 당시 기준을 연결하고 재실행한 것으로 쓰지 않는다.
4. PR에는 작업 기록과 ADR을 연결하고 결과·한계를 요약한다. 작업 기록에는 PR을 역으로 연결한다. 재개할 때 최신 main, 기록의 계획·남은 일, PR 상태와 실제 diff를 확인한다. 세션이 달라져도 같은 작업 ID를 사용한다.
5. 상태는 `계획`, `진행 중`, `리뷰 대기`, `완료`, `보류`, `취소`로 표시한다. PR 제출은 `리뷰 대기`다. 합의한 산출물·검증을 충족하고 병합이 필요한 작업은 병합까지 확인한 뒤 `완료`로 갱신한다. 실제 설치 완료는 별도 로컬 상태로 관리한다. 상태 갱신만을 위해 병합 전 완료를 추정하지 않는다.

후속 범위가 독립적인 목표로 바뀌면 새 작업 ID를 만들고 기존 작업의 남은 일과 연결한다. PR 여러 개로 나눠도 하나의 목표라면 한 작업 기록에서 추적할 수 있다. 로그는 간결하게 유지하되 결정 변경과 실패·검증 한계를 지우지 않는다.

## 기존 문서와 진행 중인 PR 전환

가드레일의 [작업 0001](work/0001-recordkeeping-guardrails.md)·PR #8을 Windows 네이티브 구현 [PR #7](https://github.com/1ocate/dotfiles/pull/7)보다 먼저 검토·병합하는 순서를 따랐다. #7은 최신 main 통합 후 [ADR 0002](adr/0002-native-windows-adapters.md)·[작업 0002](work/0002-windows-native-setup.md)에서 기록을 보완하고 검토를 재개한다. 이 순서는 #7 병합을 승인하지 않는다.

기존 날짜별 기록을 일괄 삭제하거나 과거에 없던 계획·승인을 만들어 쓰지 않는다. 관련 작업을 다음에 수정할 때 결정 근거는 ADR로, 과거 실행 결과는 출처가 있는 작업 기록으로 옮기고 기존 위치에는 링크를 남긴다. `사후 정리`임을 표시하고 확인할 수 없는 시각·근거는 `미확인`으로 둔다. 사용 문서에는 현재 필요한 버전·제약·설치 방법을 남긴다. 같은 결과의 전문을 여러 위치에 유지하지 않는다.

공개 기록에는 토큰, 인증 출력, 개인 계정·호스트 식별값과 불필요한 절대 경로를 넣지 않는다. 장비별 승인 파일을 ADR이나 작업 기록으로 복제하지 않는다. 검증에 필요한 도구 버전·환경 종류만 남긴다. 이 문서는 기록 원칙을 정의하며 자동 기록 도구나 강제 CI 검사를 구현하지 않는다.

## PR 검토 기준

- 작업의 이유·범위·계획과 실제 변경이 연결되어 있는가?
- 지속적인 결정은 ADR에, 실행 결과는 작업 기록에, 현재 사용 방법은 사용 문서에 있는가?
- 채택·병합·설치·검증 상태를 각각 근거로 구분했는가?
- 관련 기록과 PR 링크가 유효하고 기존 기록을 덮어쓰거나 비밀 정보를 복제하지 않았는가?
