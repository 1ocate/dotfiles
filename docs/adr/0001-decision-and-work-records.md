# 0001: 결정과 작업 기록의 원본 분리

- 상태: 제안
- 작성일: 2026-10-03
- 적용 범위: common의 문서·AI 협업 절차
- 관련 작업: [작업 0001](../work/0001-recordkeeping-guardrails.md)
- 관련 PR: [PR #8](https://github.com/1ocate/dotfiles/pull/8)
- 채택 근거: PR #8의 사용자 리뷰와 병합 대기
- 대체 관계: 없음

## 배경과 문제

Windows 네이티브 설치와 Neovim 호환성 작업의 검증 결과가 설치 문서에 날짜별로 추가되었다. 사용자는 구현 반영 전에 왜 작업했는지와 계획·진행 결과를 지속적으로 추적할 기준을 요청했다. 기존 가드레일은 Git·PR과 장비별 상태를 구분하지만 결정과 프로젝트 작업 기록의 원본 위치는 정하지 않았다.

## 검토한 대안

| 대안 | 평가 |
| --- | --- |
| 사용 문서에 날짜별 내용을 계속 추가 | 간단하지만 현재 지침과 과거 결과가 섞이고 기록이 파편화됨 |
| Git·PR에만 이유와 계획을 기록 | diff·리뷰에는 적합하지만 여러 PR·세션에 이어지는 결정과 계획을 찾기 어려움 |
| ADR과 작업별 기록을 두고 PR·사용 지침을 연결 | 파일 관리 비용은 생기지만 결정·실행·현재 동작의 원본이 명확함 |

## 결정과 이유

세 번째 대안을 제안한다. 지속적인 선택과 대안은 `docs/adr/`, 목표별 계획·진행·검증은 `docs/work/`에 한 번 기록하고 목록에서 찾는다. 파일은 날짜 대신 안정적인 번호와 주제로 식별한다. PR은 diff와 리뷰의 근거이며 작업 기록을 연결한다. 사용 지침에는 현재 동작과 관련 기록 링크를 둔다. 장비별 승인·적용 상태는 기존 `.local/` 기준을 유지한다.

## 영향과 재검토 조건

[기록 가드레일](../recordkeeping.md)이 작성 대상·상태·전환 절차를 정의한다. 작은 오탈자·링크 수정은 PR 본문으로 기록 부담을 줄인다. 새로운 단계별 승인, 자동 기록 도구, 설치 실행은 추가하지 않는다.

가드레일을 먼저 병합하고 Windows PR #7의 기록 정리는 후속으로 진행한다. 기존 역사 전체를 소급 작성하지 않는다. 목록 관리나 기록 중복이 실제 작업을 방해하면 이 ADR을 대체하는 결정으로 구조를 재검토한다.
